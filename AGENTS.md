### 3.2. Типы и номера проектов

* `Контракт` — коммерческий договор с внешним или внутренним заказчиком ради прибыли.
* `Тендер` — конкурсная процедура; при победе может создаваться связанный контракт.
* `Внутренний` — проект для собственных нужд ГК; с 2026 года номер договора — `1`.

Шаблон официального шифра:

```text
[Номер_договора]/[Год]-N[Номер_заказа]-[Исполнитель]
```

В имени каталога `/` заменяется на `_`. Например: `1/2026-N2-МАС` → `1_2026-N2-МАС`.

* `N0` — рамочный проект.
* `N1`, `N2`, … внутри контура того же договора `N0` — заказы рамки.
* Проект `N1` без собственного `N0` — одиночный.
* Субподрядная, финансовая или иная внешняя связь не записывается автоматически как собственная родительская иерархия. Прародитель и косвенные связи указываются раздельно.

### 5.2. Обязательные правила Master Data и производных

* Ручная правка производных спецификаций запрещена: изменения вносятся в мастер или DSL, после чего документ регенерируется.
* `work_spec` содержит `TabSpecificationWork_1`, `TabSpecificationWork_2` и `TabTableSchema`; связь основных таблиц — 1:1 по `HASH COLLECTION`.
* `HASH COLLECTION` должен быть уникальным, вычисляться формулой и соответствовать `VER COLLECTION`; застывшие токены и дубликаты недопустимы.
* Для каждой позиции используется старшая `VER COLLECTION`; версионный отбор выполняется до удаления неотгружаемых строк, чтобы решение принималось по старшей версии.
* В производные документы заказчика не включаются позиции старшей версии с `isSHIPPED=false`.
* Поставщики, закупочные цены, наценки, скидки и `COMMENT WORK` не покидают контур Master Data. Клиентские документы формируются белым списком колонок.
* В документах УСН запрещены токены `НДС` и `VAT`, включая имена выводимых колонок.
* Ручное изменение `DISCOUNT PERCENT` и `DISCOUNT MONEY` в `work_spec` запрещено; их `MODIFY FLAG=false`.
* Скрытая модификация разрешается связкой `MODIFY FLAG` (разрешение поля) и `isPROCESSING=true` (факт по позиции) и реализуется командой `ModifyData`.
* В DSL каждой производной спецификации типов 30–90 обязателен блок `"ModifyData": []` после версионного отбора и до `FinancialRound`.
* `FinancialRound` пересчитывает зависимые финансовые поля банковским округлением; в `NewData` указываются только исходные изменяемые значения.

Подробная схема: [README-work_spec.md](./03__Проект/07__template-excel/20__work_spec/README-work_spec.md).

## 6. ETL-ПРОЦЕССОР И БИБЛИОТЕКИ

### 6.1. Архитектурный контракт ProcessingTable

Сигнатура:

```m
(
    _configJSONIndex as text,
    optional _pathExcelBook_1 as text,
    optional _pathExcelBook_2 as text,
    optional _pathExcelBook_3 as text,
    optional _pathExcelBook_4 as text
) as table => ...
```

* JSON извлекается из `TabConfigJSON` текущей книги по `IDconfig`.
* Поддерживаются от 1 до 4 таблиц.
* Конфигурация разбивается на МакроБлоки `"1"`, `"2"`, …; состояние проходит конвейер `Table_Initial → … → Table_Final`.
* Ключи МакроБлоков — только строковые целые числа; исполнение — в числовом порядке.
* Внутри одного МакроБлока каждая BI-команда вызывается не более одного раза.
* Порядок команд задается фиксированным конвейером приоритетов ядра, а не порядком ключей JSON.
* Ровно одна команда слияния допускается только в Таблице 1.
* `ConfigValidation` выполняется до обработки; критические ошибки структуры останавливают запуск.
* `ValidationData` является этапом конвейера; `StrictBlock=true` аварийно останавливает генерацию при невалидных данных.

Состав команд и сигнатуры развиваются. Актуальные источники:

1. [README-etl-processor.md](./03__Проект/05__pq-script/01__general/03__etl-processing/README-etl-processor.md);
2. новейший `ProcessingETL - процессор rev.*.m` в каталоге `03__etl-processing`.

### 6.2. Библиотеки Power Query

* `GeneralFunction` — системные сервисы.
* `UtilsFunctionScalar` — скалярные валидаторы `fv..._scalar`.
* `UtilsFunctionVector` — векторные трансформации `ft...` и табличные валидаторы `fv...`.
* `HandbookFunction` — нормализация НСИ и проекции корпоративных справочников.

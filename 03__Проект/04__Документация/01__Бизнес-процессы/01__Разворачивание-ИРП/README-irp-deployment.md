# РАЗВОРАЧИВАНИЕ И ПРИЕМКА ИРП

**Версия процедуры:** 1.0
**Дата:** 18.11.2026
**Нормативное основание:** [Канон ИРП](./README-irp-canonical.md)

## 1. Роли и контрольные принципы

- **Руководитель проекта (РП):** утверждает паспорт, места `00__draft`, состав фактических контрагентов и предметное наполнение.
- **AI-агент / оператор:** выполняет согласованные файловые операции, документирование и проверки.
- **Хозяин:** отдельно подтверждает каждую Git-мутацию и переход к канонизации конкретного проекта.

Обязательные принципы:

1. Сначала фактический read-only аудит, затем изменения.
2. Новый ИРП и канонизация существующего — разные сценарии.
3. Содержательные данные не копируются из других проектов.
4. История журнала и фактические ошибки не переписываются.
5. Приемка выполняется по [чек-листу](./templates/checklist-irp.md).

## 3. Сценарий A. Новый ИРП

### Шаг 1. Подготовка

1. Прочитать `AGENTS.md` профильного проекта, настоящий канон и процедуру.
2. Проверить, что целевой путь соответствует файловому шифру.
3. Проверить, не существует ли уже ИРП; при существовании перейти к сценарию B.
4. Зафиксировать исходное состояние и ограничения в журнале профильного проекта.

### Шаг 2. Файловый каркас

1. Создать десять корневых разделов.
2. Создать `03__Проект\temp` и `03__Проект\tools`.
3. Создать применимые вложенные контуры документации, спецификаций, ТЗ, договора, счетов, затрат и логистики.
4. Создать четыре категории переписки.
5. Создать `00__draft` только в местах, утвержденных РП.
6. Не создавать `00__raw` и `GEMINI.md`.

### Шаг 3. Документы

1. Заполнить `AGENTS.md` по [шаблону](./templates/AGENTS.md).
2. Создать и заполнить все 12 базовых README из [канона](./README-irp-canonical.md#42-базовый-комплект--12-readme).
3. Сформировать единый `README-mail.md` с четырьмя реестрами.
4. Создать `ai-{файловый-шифр}.md` с тематическим разделом и единым разделом `100`.
5. Заполнить паспорт проекта; не оставлять юридически значимые поля неопределенными без отметки `ТРЕБУЕТ РЕШЕНИЯ РП`.
6. Пустые обязательные каталоги подготовить к Git через `.gitkeep`, если в них нет содержательного README.

### Шаг 4. Git — только после подтверждения

1. Проверить `.gitignore` по [шаблону](./templates/gitignore.txt).
2. Получить отдельное подтверждение и выполнить `git init`.
3. Проверить автора, не меняя глобальную конфигурацию без согласования.
4. Проверить индекс: отсутствуют `desktop.ini`, присутствуют обязательные пустые каталоги через `.gitkeep` или README, `00__draft` не игнорируется.
5. Получить отдельное подтверждение коммита и создать init-коммит по [шаблону](./templates/init-commit.md).
6. Remote и push не выполнять без отдельного поручения и подтверждения.

## 4. Сценарий B. Канонизация существующего ИРП

1. Выполнить read-only сканирование и сохранить перечень расхождений.
2. Проверить фактическое содержимое, а не только имена каталогов.
3. Не удалять и не перемещать проектные данные ради формального соответствия.
4. Найти все `00__raw`; для каждого проверить содержимое и конфликт имени с `00__draft`.
5. После согласования переименовать `00__raw` в `00__draft`; если `00__draft` уже существует, остановиться и запросить решение РП о слиянии.
6. Сохранить существующий бизнес-каталог `01__raw_spec`.
7. Создать отсутствующие обязательные документы, не переписывая исторические журналы.
8. Если существует `GEMINI.md`, перенести действующие нормы в `AGENTS.md`, проверить полноту и удалить `GEMINI.md` только в рамках согласованной канонизации.
9. Четыре старых почтовых README не объединять молча: проверить записи и перенести их в единый `README-mail.md` без потерь.
10. Существующие журналы не перенумеровывать; новые записи исполнения размещать в едином разделе `100`.
11. Сохранить `77__Контрагенты`; замену шаблонных контрагентов фактическими выполнять по решению РП.
12. Дополнительные `00__draft` автоматически не создавать.

## 5. Приемка

### 5.1. Файловая проверка

Проверить фактическим сканированием:

- десять корневых разделов;
- `AGENTS.md` и отсутствие `GEMINI.md`;
- все 12 базовых README;
- единый `README-mail.md` и четыре его раздела;
- журнал и единый `## 100. ИСПОЛНЕНИЕ ПРОМТОВ`;
- `temp` и `tools`;
- отсутствие любого каталога `00__raw`;
- сохранение применимого `01__raw_spec`;
- `00__draft` только в утвержденных местах;
- корректность ссылок и отсутствие незаполненных обязательных полей без статуса решения РП.

### 5.2. Git-проверка

Если Git инициализирован:

1. Проверить `.gitignore`: `00__draft` не исключен, `desktop.ini` исключен.
2. Сверить файловую структуру с `git status` и содержимым индекса.
3. Убедиться, что обязательные пустые каталоги представлены `.gitkeep` или README.
4. Проверить полное описание init-коммита.
5. Проверить автора коммита.
6. Remote и push оценивать отдельно от обязательной приемки ИРП.

### 5.3. Регистрация результата

В журнал заносятся:

- выполненные операции;
- измененные пути;
- отклонения и решения РП;
- фактические проверки;
- Git-хеш, если коммит был отдельно разрешен и выполнен.

Невыполненный пункт нельзя отмечать как пройденный. Для отложенных Git-операций указывается статус `ОЖИДАЕТ ПОДТВЕРЖДЕНИЯ`, а не `ВЫПОЛНЕНО`.

## 6. Критерии завершения

Процесс завершен, когда:

1. обязательный каркас и документы существуют физически;
2. отсутствуют `00__raw` и `GEMINI.md`;
3. реестр переписки и журнал соответствуют канону;
4. паспорт проекта заполнен;
5. чек-лист содержит фактические результаты;
6. журнал содержит запись исполнения;
7. Git-операции либо приняты по коммиту, либо явно зафиксированы как ожидающие отдельного подтверждения.

## 7. Автоматизация

Утилита разворачивания может быть создана в `03__Проект\tools` только после отдельной оценки целесообразности. Она должна проверять тот же чек-лист и не обходить подтверждения Git. Создание утилиты не входит в обязательный минимум настоящей процедуры.
